## 依赖图

```text
00 的阶段确认 → 01 → 02 → 03 ─┐
                         └→ 04 ─┼→ 05 ─┐
                         └────────→ 06 ─┼→ 07 → 内测 → 08 → 09
```

03 与 04 同一最小闭环迭代推进：数据契约稳定后即可开始周报，不等对话 UI 精修。06 的基本安全措施从 01/02 就开始，不能等最后才加草稿保存或备份。

安全门禁按实际依赖判定，以表格和各计划正文为准。多人并行只允许不同模块或隔离 worktree，不允许多个 AI 同时改同一目录的共享契约。

## 里程碑

- M0：确认基础方向与私有仓库，工程能在 Linux 真实壳启动。
- M1：记录到周报的 Mock 闭环；含草稿恢复、事实统计与回链。Mock 不代表 AI 产品已成立。
- M2：获批真实 AI + 额度 + 数据生命周期，完整 P0 可内测。
- M3：Linux 安装包实际试装、升级与恢复验证，开始跨周内测。

产品定义中的三周节奏用于尽早收集周报反馈，不承诺以上计划固定工期。每项实现开始时评估规模。

## 执行与完成记录

每次启动一个 plan：检查门禁 → 更新为 in-progress → 完成最小切片 → 执行验收 → **提醒原子化提交** → 填证据 → 再更新为 done。受阻则标 blocked 并注明问题，不为了推进状态而猜测。

一个 plan 可包含多个原子提交；一个提交只解决一个独立问题，并包含必要测试与文档。每个可验证切片完成后就提醒，不把多个 plan、功能或无关重构堆成一次提交。提醒不代表用户已授权执行提交或推送。

完成记录使用统一字段：

- 实际变更文件：
- 原子提交边界与提醒记录（已获授权执行时记录提交哈希）：
- 实际执行命令与结果：
- 测试环境与覆盖范围：
- 未覆盖/受阻项：
- 剩余风险与后续任务：

开发者可在每个 plan 下细拆任务，但不得默默扩大产品范围或改变依赖。所有远程发布、邀请协作者、公开可见性改变另行确认。
