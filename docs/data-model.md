# 数据模型与生命周期

状态：逻辑设计提案，不是已批准的 SQL Schema。字段名、枚举与数据库实现须在对应 plan 中确认。

## 1. 实体

| 实体 | 最小职责 | 核心数据 |
| --- | --- | --- |
| Draft | 输入与崩溃恢复 | ID、原始文本/消息、记录日期、时区、修改版本、最近持久化状态 |
| Entry | 正式记录 | 稳定 ID、原文、五栏、创建/修改时间、日期、版本、来源与确认状态 |
| Action | 投入的确定性统计单元 | ID、记录 ID、事实描述、轻量目标引用、分钟数或 null、约数标记、来源 |
| PositiveFact | 用户认可的正反馈 | ID、事实候选、确认状态、关联目标、来源；明确没有与未确认分开 |
| Review | 可编辑的周期产物 | ID、模式、区间、时区、输入版本、统计快照、叙述、引用、草稿/确认/过期状态 |
| Summary | 派生记忆与缓存 | 层级、输入 ID/版本、Prompt/模型版本、来源链、有效性；不是事实源 |
| AIRequest | 可追踪的调用任务 | 请求/任务 ID、用途、输入版本、提供商、状态、用量、错误码，不重复存敏感 Prompt |
| Settings | 非秘密偏好 | AI 开关、口吻、授权版本、时区与数据操作偏好 |

正式 Goal 实体到 P1 再设计；P0 若需要引用，可使用用户可编辑的轻量标签，不自动创建或强制设目标。

密钥不存入 Settings；额度的权威来源依部署方案确定。客户端本地次数只能是原型计量，不能承诺真实服务计费可靠。

## 2. 五栏的实现口径

- 目标：可空，多行动可分别关联；单条不一定只属于一个目标。
- 状态：建议可选词或类别，禁止情绪分数；形式待用户确认。
- 投入行动：每项可单独统计，未知时长为 null，不能自动变 0。
- 正反馈：候选事实与用户确认分离，只有已确认事实计入进展统计；没有好事不是失败。
- 反思：自由文本，AI 引子与用户反思分开，不计完成率或分数。

「必填两项」与不阻断保存的冲突需先确认。设计建议支持空值和跳过状态，避免以后通过数据库强约束逼迫用户填表。

## 3. 来源引用

建议引用结构包含 `entryId + entryVersion + actionId/factId（可选）+ 原句位置或片段`。

- ID 存在不等于结论正确，还需校验内容与引用事实一致。
- AI 只能引用输入中允许的 ID，不能凭空生成新的记录。
- 修改原文后旧片段可能失效，应显示过期或重新定位，不假装仍是原文。
- 记录删除后无法继续导航到原文；受影响叙述与缓存按删除政策处理。

## 4. 聚合定义

- 复盘区间内部建议使用半开范围 `[start, end)`；界面清楚显示实际包含的日期。
- 记录归属按显式记录日期与时区，不直接用服务返回时间决定当天。
- 总时长只加已知分钟数；同时展示未知时长的行动数量；约数保留「约」的说明。
- 行动次数按唯一 Action ID；重复调用/保存不能生成重复行动。
- 正反馈次数按唯一已确认 PositiveFact ID，不把 AI 表扬次数当进展。
- 多目标行动需明确主目标或分摊规则，不能把一小时分别加到两个目标又加总成两小时。
- 目标缺失的行动进入未关联组，不丢弃。
- 无输入产生空状态，不生成「你这一周充实而有意义」之类无依据结论。

分摊、重复记录识别、有效记录指标等未定规则在实现前确认。P0 不需要复杂自动去重算法，但必须防同一保存请求重放。

## 5. 状态与并发

- 保存反馈区分未保存/保存中/已保存/失败，失败后可重试且不丢内容。
- AI 请求区分排队/运行/成功/失败/取消；旧版本成功结果不得覆盖当前草稿。
- 复盘草稿、用户确认版与输入过期状态分开表达；旧确认版不能自动替换成新 AI 版本。
- 应用用例明确事务范围与幂等键；多窗口策略在支持多窗口前确定，不假设只有单一写入者。

## 6. 迁移、备份、导出与删除

- Schema 版本递增，迁移前做一致性备份，失败保留原数据库。
- JSON 完整导出带格式版本、实体与关系，不含密钥；Markdown 面向阅读，不替代可恢复备份。
- 备份应有完整性检查与实际恢复测试。恢复前备份当前数据、二次确认，避免覆盖唯一副本。
- 删除涉及原文、五栏、摘要、缓存和引用；已确认复盘中的派生个人内容按明确政策删除或脱敏。
- 应用内备份的保留与清理政策需确认；用户另存或上传的导出文件无法由应用保证删除。
- 本地明文、加密数据库与备份加密方案都未定，不能因为文件在本机就宣称加密。
